# Task 23 fix round 1 — findings (from the review at abad9db) and controller rulings

## Important 1 — a source change that stops can never verify (transfer.ts:240, :172-180, :287)
Each pass compares this Mac's side with `plan.expected`, the manifest frozen at Freeze. That baseline never changes. Once a file differs from the manifest after Freeze, it differs on every later pass: passes 2 and 3 copy and re-hash the whole root again for nothing; the outcome is always `external_writer`; the blocker says "close whatever writes there, then resume", but a resume uses the same manifest and blocks again. The spec (Destination replicas and divergence) says "detected source changes cause another pass" and "after three unstable passes" stop — passes that can succeed once the writer stops. An IDE running `git status` rewrites `.git/index`; one refresh after Freeze blocks the transaction permanently. The pull direction has the same problem.

Controller ruling (binding): a pass is stable when this pass's source re-scan equals the previous pass's re-scan and the checksum dry run is clean. The per-root outcome returns the verified scan (the file list that actually landed), and Task 26/27 seal and accept that scan instead of the frozen manifest's file list (the manifest digest stays the transaction's identity). Three passes without two consecutive equal scans (or with a dirty dry run) → `external_writer`. A resume re-runs passes and converges. Add a test: a source edited once during pass 1 and left alone after that verifies on pass 2; and one that keeps changing still ends in `external_writer`. Name in the blocker which side the difference came from (source, or the far replica / local copy), not always the source.

## Confirmed gap (was ⚠️) — the far rsync's version is never verified (brief: "Pin/verify a compatible rsync feature set")
The far end must be rsync ≥ 3.2.3 (`--mkpath`, `-s`). Nothing checks it, and a missing or too-old far rsync makes the local rsync exit 12, which maps to `disconnected`, so Task 27 may reconnect and resume in a loop (rsync.ts:192). Fix: probe the far `rsync --version` once per transfer over the same master and return a typed blocker when it is missing or older than the minimum; after an exit 12/255, check whether the master is still up before reporting `disconnected`. Tests for both.

## Confirmed gap (was ⚠️) — the doctor never flags the openrsync fallback (brief step 1: "the system binary is a fallback the doctor flags")
`probeRsync` exists but no doctor calls it. Wire it into `archi doctor` on macOS: a missing bundled rsync with only the system openrsync present is a flagged (warning or failing, match how doctor reports other unsupported configurations) row that names the fix. Test it where doctor rows are tested today.

## Promoted minor (controller ruling) — the placeholder host could resolve (rsync.ts:16)
If the master is gone, ssh falls back to connecting to `archi-remote` directly; a MagicDNS short name or search domain could resolve it and rsync would push fleet files to an unintended host. Use a name that can never resolve (`archi-remote.invalid`, RFC 6761), with a test asserting the argv.
