# Task 28b — fix round 1 findings (from the task review at d07f935)

I1. fleet-recover.ts:298-311 — the relay starts the new owner before it stops the old one. Machines are told in registry insertion order (local first), so `--force-owner local` adopts (revives, activates, up to 2 min) on the Mac before vault is sent `deactivate`: both run for that window with nothing unreachable. Fix: relay to every machine the record does not name first, then to the named owner; test the `recover.adopted` order.

I2. service.ts:112 — `ran = ownership.isOwner()` is read before the `supersede` await (:113-114). DestinationHandover.supersede queues behind an in-flight `runActivate` on `serial`; if that activate read the gateway just before the force landed, it installs g+1 naming this machine, promotes the state and starts windows, then `discard` runs and `installCommitted` names another machine (:116), and because `ran` is still false, `deactivate` never runs (:122) — owner.json names another machine while its terminals keep running. Fix: read `isOwner()` after the supersede await (test it).

I3. service.ts:99-116 (with `setGateway` at :105) — `ownership.adopt` installs whatever record a token client sends without asking the gateway, even on daemons that have an authority route; a record above the gateway's generation then permanently defeats "gateway wins at start" there (adoptAtStart ignores lower records); `gatewayMachineId` is rewritten even when the call returns `adopted: false`. Fix: when the daemon's authority route is available, ask it after `setGateway` and adopt only what it returns (or require it to equal the relayed record); fall back to the relayed record only when the gateway cannot be asked; rename the gateway only when the record is taken.

I4. state.ts:57, service.ts:108, pinned by service.test.ts:324 — at start a gateway record at an equal generation naming another machine is ignored, and state.ts:46 appoints this machine owner at g0 when a gated fleet has no owner.json, so both run (the M2 remote-only fixture path). Controller ruling (progress.md, "Task 28b: Ruling (implementer concern 1…)"): a reachable gateway record wins over a daemon's cache when its generation is higher, or equal with a different owner while no handover journal is open on that daemon; a lower generation is ignored. A gated fleet (fleet.json names a gateway) with no owner.json starts owning nothing until the gateway names it. Update the pinning test.

I5. service.ts:107-118, startup.ts:41, state.ts:117-118 — adoption at start lifts a quarantined journal: `open()` returns undefined for a quarantined journal, so a higher record naming this machine is taken, `installCommitted` drops `surrendered`, then `unhold()` and `activate()` run on the pre-handover state.json (the reviewer confirmed with a probe: a quarantined journal plus a gateway answering a committed handover to this machine went writable and ran activate; the controller's later `handover.activate` then fails). Fix: with a quarantined journal, never adopt a record carrying a `transaction` (a forced record never carries one); never activate on a record whose committed transaction targets this machine without its journal; test it.

I6. fleet-recover.ts:150 and :316, pinned by fleet-recover.test.ts:162, :309 — the risk text and actions promise that a machine not reached "takes this record when its daemon next starts and reaches <gateway>", but a Linux daemon that is not the gateway reaches it only through `configDir()/machines.json` (gateway/client.ts:156-162), which no Linux setup writes — vault never asks and keeps running as owner while the operator is told not to act. Fix: only the gateway machine and machines with a controller registry consult the gateway at start; for every other unreached machine print "run this again once it answers" and say so in the risks.

Promoted (Ruling: each fails open or reports a recovery that did not happen, in the one command meant to end an outage):
M2+M8. fleet-recover.ts:137 and authority.ts:180 count the gateway record at `generation`, not the g+1 its preparing/ready transaction targets, so a force can land at the unreachable parties' journal generation, supersede nothing, leave the chosen owner frozen and still print "recovered"; and a reached daemon that answered `adopted: false` still ends with `recovered` and exit 0. Fix: count a record with a non-committed transaction at g+1 in both places; end nonzero, not "recovered", when the chosen owner did not take the record.
M4. fleet-recover.ts:218-221 allows `--gateway` when the current gateway answers `refused` — that gateway is alive, so the fleet gets two authorities. Allow a replacement only when the current gateway is unreachable (or its record is corrupt).
