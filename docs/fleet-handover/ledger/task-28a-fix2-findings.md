# Task 28a — fix round 2 findings (from the scoped re-review at 8db9b47)

N1 (Important). The lock's holder is told dead or alive only by `kill(pid, 0)` (src/controller/helper.ts:50-56, :116; EPERM counts as alive). After a SIGKILLed helper or a reboot, the pid in `handover.lock` can belong to any other process (a daemon started at boot, another user's or root's process), and then start, `--resume`, `--abort` and `--forget` all refuse until that process exits or a person deletes the file — the test at test/handover.test.ts:814 shows it with an unrelated `sleep` pid. A stale lock naming the taker's own reused pid makes the taker refuse itself. The app never sees the remedy: the launcher's pre-check reads only the socket (handover.ts:348), so the child launches and refuses, the "remove <lock>" text goes to handover.log, and the app gets "exited (code 1) before it listened; <log> says why" (:364).
Fix: a holder is gone when the lock predates the machine's boot, or when the process now holding that pid started after the lock was written (e.g. record the holder's start time in the lock, or compare `ps -o lstart= -p <pid>` with the lock's mtime; the taker's own pid is never a live holder). Test with a live unrelated process that started after the lock was written. And the launcher reports a lock it cannot take (a live holder that does not answer) as its `handover.result`, not only in the log.

N2 (Ruling — the contract says the controller re-emits the current phase once any `handover.blocked` decision is answered). The prepare decision (src/controller/handover.ts:318) does not re-emit, so a replay during the following `handover.prepare` call still shows the decision pending. Re-emit there too; test it.
