Whole-PR review of https://github.com/linusroxbergh/svall/pull/2 at `6d7915be` (19 commits on main `c1905f05`).
Report-only: nothing was fixed, pushed or commented. Line numbers are at `6d7915be`, svall paths.

  the monorepo. Ten area chunks: svalld destination, svalld source, svalld boot/config/runtime, fleet runtime and

## High

**H1. A shipped Svall.app cannot install a Linux companion.** 80 / G high / S high. `apps/desktop/mac/build.sh:57`
- *Failure:* `pnpm release` → `app-build.sh` → `build.sh release` pins the x64 companion in
  `Contents/Resources/release/release.json` as `file://$MAC/build/companions/…tar.gz`, a path on the builder's disk,
  and copies only `releases/*/` into the app. On a user's Mac, Add Machine, `svall host add` and `host upgrade` reach
  `downloadCompanion` (`packages/cli/src/controller/install.ts:81-82`, `readFileSync(fileURLToPath(url))`) and fail
  with ENOENT. On the builder's own Mac it breaks at the next build, because `rm -rf $COMPANIONS` runs first.
  `release.yml` never builds the app, and nothing uploads the archive. After a Sparkle update that changes the release,
  a fleet on Linux can neither be upgraded nor handed back. `--release <archive>` (`controller/host.ts:289`) is the
  only way out, and it hits H6. The PR body, `docs/remote-machines/README.md:34` and `setup.md:99-101` all say the app
  carries the companion. `release-scan`, which refuses `/Users/` paths, never runs on the carried tree.
- *Fix:* carry the archive in the app and resolve it against `releaseRoot()`, or build the carried controller with an
  https URL base whose bytes `pnpm release` publishes. Run release-scan on the carried tree.

**H2. Notarization will reject every release.** 85 / G high / S high (partly valid). `scripts/sign.sh:7-14`,
`apps/desktop/mac/build.sh:58`
- *Failure:* every `CONFIG=release` build now carries `Contents/Resources/release/bin/rsync`, built from source by
  `scripts/build-controller.mjs` and stripped with `strip -S`. `codesign -dvv` on a built tree shows
  `adhoc,linker-signed` with no TeamIdentifier. `sign.sh` (unchanged from main) signs only Helpers, Sparkle and the
  app, and signing the outer app does not sign Mach-O files under Resources. `release.sh`'s `notarize dist/Svall.zip`
  comes back Invalid, so no Svall version can ship, flag on or off. `--adhoc` dry runs hide this, and the ledger's
  task-12 report already warned that bin/rsync is unsigned.
- *Notes:* sol notes that `sign.sh` does not sign the carried `node/bin/node` either; it passes today because it ships
  with Node.js Foundation's Developer ID, runtime and timestamp. sol's "partly" is only that a notary verdict cannot be
  proven from source.
- *Fix:* sign `Contents/Resources/release/bin/rsync` (and re-sign the carried node with `node.entitlements`) in
  `sign.sh` with `--options runtime --timestamp` before the app, or ship rsync in Helpers.

  resolves `~/.svall-work`. The helper then emits `online(local)` with the release daemon's port and token.

**H5. A prepare retried after a crash in the Git import seals destination edits, which rsync then deletes.** 55
(reviewer 68, probe) / G medium / S critical. `packages/svalld/src/handover/destination.ts:444,457`
- *Failure:* `landedDigest` is journaled at 444, `importGraphs` runs at 450, and the seal is written in the
  `finally` (453-462). The daemon dies inside the import (reboot, OOM, kill) and the user edits `work/bo/index.ts`
  while it is down. A process that dies never runs its `finally`. The retried prepare has `verified` true (420), so it
  skips the landed check (435). The claim's seal record has no files, so line 457 scans the root as it is now and seals
  the edits as the handover's own. If that prepare blocks again, the re-transfer's claim accepts them as imported (314,
  `replicas.ts:200`) and `rsync --delete` reverts them. On abort, `sealAs(back)` (907-909) seals them as generation-g
  content, and the next handover deletes them. This breaks "never silently deletes destination-only work".
- *Notes:* this is not the last review's A1 (pre-prepare abort); that review's M2 fix is what created this retry path.
  An untracked file written during the seconds-long import is absorbed the same way. Probe: `C1/tail-crash-import.ts`
  in the review scratchpad (not kept).
- *Fix:* write the seal from the verified landed list before journaling `landedDigest`, then add only the import's own
  Git-directory writes; or treat `verified` as false when the seal has no files for a carried root.

**H6. The app's release name never matches the tag its companions are published under.** 70 / G high / S high.
`scripts/release.sh:63,116`, `scripts/release-stage.mjs:49`
- *Failure:* `release.sh` runs `pnpm app:build` (63) before `git tag "v$VERSION"` (116). `build.sh` names the release
  `describeVersion()` (`git describe`), for example `v0.2.1-26-gX` for Svall 0.2.2. `release.yml` builds companions

## Medium

**M1. Quitting the app during a handover stops the daemon its helper still needs.** 70 / G medium / S high. Four
reviewers found this independently. `apps/desktop/mac/Sources/Svall/QuitFlow.swift:92`,
`packages/svalld/src/fleet.ts:303`, `packages/svalld/src/ownership/guard.ts:43`
- *Failure:* nothing in `confirmQuit`, `applicationShouldTerminate` or `ShellRouter.closeAll` checks for an open
  handover. Window close and app updates also quit.
  - Mac→Linux (route `.local`): the quit sends `quit.stop`, and the page calls `fleet.stop`, which is classed `'read'`
    and so passes on a frozen source. `stopAll` skips `endAll` but still emits `'stopped'`, and `bin.ts:55` exits.
    The launchd plist has no KeepAlive (`launchd.ts:51`). The helper's calls fail `daemon_down` after 4 retries
    (`controller/handover.ts:99`), with some terminals rested and the rest running. Nothing restarts the daemon until
    the app reopens.
  - Linux→Mac: the route stays `.remote` for the whole run, so `elsewhere()` is true. `FleetDaemon.kill` sends SIGTERM
    to the destination daemon and runs `tmux kill-server`, while the alert says "Your characters keep working on the
    machine this fleet runs on".
  - Both cases are journaled, and reopening plus Resume recovers. This still contradicts
    `docs/remote-machines/handover.md:38` ("Quitting the app … does not stop a handover"). Archipelago's daemon
    outlived the app (progress.md: "survives logout and app quit PASS"); main's quit stops it, and the merge kept
    main's quit.
- *Fix:* while a handover journal is open or a HandoverSession helper is live, skip both `quit.stop` and
  `FleetDaemon.kill`, or have `stopAll` refuse to emit `'stopped'` with an open journal. Otherwise ask before quitting.

**M3. A symlinked config.json (stow, home-manager) is forked by the split and then stops the daemon.** 55 (C3 probe 85)
/ G medium / S medium (partly valid). Flag off. `packages/svalld/src/config.ts:112`
- *Failure:* main supported and tested a linked config.json written through its link (`c1905f05` config.test.ts:82).
  `initConfig` renames the link itself to `config.json.bak` and writes plain `fleet.json` and `node.json`. Dotfile
  edits are then ignored. When `stow -R` or `home-manager switch` puts `config.json` back, `configRefusal` throws
  InvalidConfig and svalld does not start until the user merges by hand. Ruling R8 covers a config.json put back, not
  one a dotfile manager recreates. `migration.md` does not mention symlinks. sol's "partly": the migration retires the
  legacy file on purpose, so the bug is the silent fork and the refusal, not the loss of legacy syncing.
- *Fix:* when `config.json` is a link, split from its target and say to link `fleet.json`/`node.json` instead; or
  treat a link to the same target as `.bak` as already migrated. Document it in `migration.md`.

**M4. A pending freeze decision tells the user to answer in a terminal the sheet hides.** 65 / G medium / S medium.
`apps/desktop/web/src/store/handover.ts:61`, `selectors.ts:157`, `handover.ts:304`
- *Failure:* while a decision such as agent_blocked is pending, `toggleHandover(false)` is refused. The close button

  makes `isVeiled` true, so `TerminalArea` hides every surface, native ones included (`m.hide`). The hint says "answer

**M5. At boot the gateway machine's daemon can start on a stale owner record.** 60 / G medium / S high (partly valid).
`packages/svalld/systemd/svall-svalld@.service.in:5`, `packages/svalld/src/gateway/client.ts:173-177`,
`packages/svalld/src/handover/startup.ts:73-79`
- *Failure:* both units are `Type=simple` with no ordering between them (the daemon unit has only
  `After=network.target`). The daemon's `adoptAtStart` connects to the local gateway socket once. ENOENT or
  ECONNREFUSED rejects at once; the 10 s `GATEWAY_START_MS` only bounds a slow answer. The daemon then starts on its
  cached record, and nothing asks the gateway again until the next restart.
- *Example:* Linux owns the fleet at g; its daemon is down or crash-looping while its gateway stays up; the user runs
  `fleet recover --force-owner mac` through that gateway (g+1); the machine reboots, and its daemon runs writable at g
  with no journal while the gateway names the Mac. A recovery while the whole machine is off cannot happen this way,
  because the gateway lives on that machine, as sol pointed out; a replacement gateway needs the old machine dealt
  with first. A destination that committed just before a reboot likewise stays held.
- *Notes:* this literally fits "temporarily unreachable", but it defeats "a reachable gateway record wins". The
  controller routes by the gateway, so the harm is local agents writing on the stale machine.
- *Fix:* retry ENOENT/ECONNREFUSED on the local socket until `GATEWAY_START_MS` when the gateway is this machine.
  After=/Wants= alone is not enough, because Type=simple does not wait for listen.

**M6. The connect helper keeps a dead forward after a Linux daemon restarts on a new port.** 55 / G medium / S high.
`packages/cli/src/controller/connect.ts:101,130`
- *Failure:* named fleets on Linux get `node.json` port 0 (`linux/provision.ts:118`), and their unit has
  `Restart=always`, so `host upgrade`, a crash or an OOM moves the port. `goOnline` reads connection-info once.
  `alive()` is `master.check()` plus a local accept on the `-L` forward, which the ssh master always accepts, and
  `hold()` compares only `keyOf(owner)`. The window's API socket stays dead until the window reopens or a handover
  calls `reconnect()`. The private fleet keeps a fixed port, so only named fleets are hit, which is why this stays
  Medium.
- *Fix:* re-read connection-info over the master on each hold tick, or handshake through the forward, and treat a
  changed port or token as ended.
