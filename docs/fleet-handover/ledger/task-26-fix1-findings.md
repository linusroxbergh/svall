# Task 26 fix round 1 — findings (from the review at 02905ad) and controller rulings

## Important 1 — after activation, the new owner admits phones by the destination's old login list (destination.ts:102-106, exposing api/server.ts:74-75)
`startApi` copies `opts.mobile.logins` and `origins` into constants at startup. `adopt` then replaces `config.mobile` with a new object, so the API never sees the imported lists. Until a restart, the now-writable owner accepts phone logins and extra origins from the destination's pre-handover fleet.json. A stale empty list means `identityOf` admits every tailnet login (server.ts:66-70) — the default for a destination fleet.json seeded before the user restricted logins on the source. Revoked logins regain write access. Fix options: have the API read logins and origins through the shared config (a getter, or `opts.mobile` read per request), with `adopt` mutating `config.mobile` in place; or end activation with a daemon restart. Add a test that a login removed in the imported fleet.json is refused after `activate`.

## Confirmed gap (was ⚠️) — activation starts every windowless slot (destination.ts:305-308)
This includes characters that were already dormant on the source before freeze. Normal startup never auto-revives, and the spec's abort revives "only terminals that handover stopped"; the manifest carries nothing that tells the two apart.
Controller ruling (binding): activation revives only the terminals the handover rested; a character that was dormant before freeze stays dormant on the destination. Use the cheapest faithful signal that travels with the snapshot — prefer a marker the source's rest writes into each dormant slot record it creates (naming the transaction), so the snapshot carries it; otherwise the source's `stoppedTerminals` carried in the manifest. If the signal needs a source-side change (rest.ts or source.ts), keep it to the minimum; the controller resolves any cherry-pick conflict. Test: a slot dormant before freeze stays dormant after activate; a rested slot is revived.

## Promoted minor (controller ruling) — a pool failure releases the queue while workers still run (destination.ts:95-99)
If `recordSlot` throws (a journal write fails), `Promise.all` rejects and the serial queue releases while other workers keep going; a retry could then open the same slot twice — two agents resuming one session. Fails open against "activates exactly once". Use `allSettled`, or catch inside the worker, so the call settles only after every worker has. Test it.
